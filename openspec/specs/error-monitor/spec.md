## Requirements

### Requirement: 统一的错误上报协议
系统 SHALL 将所有来源（渲染错误、全局同步异常、未捕获 Promise rejection、静态资源加载失败、手动上报）产生的错误统一收敛为同一个 `ErrorReport` 数据结构，包含来源标识、严重级别、错误消息、堆栈、发生时间、当前页面地址、User Agent 等字段；不同来源仅通过来源标识字段区分，不允许各来源自行定义不同的报告结构。

#### Scenario: 不同来源产出同一套字段结构
- **WHEN** 一次全局同步异常和一次 React 渲染错误分别被捕获
- **THEN** 两者生成的错误报告具有完全相同的字段集合，仅来源标识与是否携带组件堆栈不同

### Requirement: 捕获全局未处理的同步异常
系统 SHALL 监听全局的错误事件，捕获所有未被应用代码 try/catch 接住的同步异常（包括事件处理函数、定时器回调中抛出的错误），生成一条来源标记为"运行时错误"的错误报告。

#### Scenario: 事件处理函数中抛出未捕获错误
- **WHEN** 用户点击触发的事件处理函数中同步抛出一个未被捕获的错误
- **THEN** 系统捕获该错误并生成一条来源标记为"运行时错误"的错误报告，字段包含错误消息与堆栈

### Requirement: 捕获未处理的 Promise rejection
系统 SHALL 监听未处理的 Promise 拒绝事件，捕获所有没有被 `.catch()` 或 try/catch 包裹的 `async`/`await` 异常，生成一条来源标记为"未处理的 Promise 拒绝"的错误报告。

#### Scenario: async 函数中的异常未被处理
- **WHEN** 一个 `async` 函数内部抛出异常且调用方没有对其进行捕获处理
- **THEN** 系统捕获该未处理的拒绝并生成一条来源标记为"未处理的 Promise 拒绝"的错误报告

### Requirement: 捕获静态资源加载失败
系统 SHALL 在事件捕获阶段监听资源加载错误，识别图片、脚本、样式等资源元素加载失败的情况，生成一条来源标记为"资源加载失败"的错误报告，包含加载失败的资源地址；不得使用非捕获阶段的监听方式（会漏报资源类错误）。

#### Scenario: 图片资源加载失败
- **WHEN** 页面中的某个图片元素因资源不可访问而加载失败
- **THEN** 系统捕获该失败事件并生成一条来源标记为"资源加载失败"的错误报告，包含该资源的地址

### Requirement: React 渲染错误的局部捕获与自定义兜底 UI
系统 SHALL 提供一个 `ErrorBoundary` 组件，捕获其包裹子树在渲染阶段、生命周期方法、构造函数中抛出的错误，阻止异常继续向上传播并展示调用方传入的兜底 UI，同时生成一条来源标记为"渲染错误"、包含组件堆栈的错误报告。

#### Scenario: 子树渲染抛错时展示兜底 UI
- **WHEN** `ErrorBoundary` 包裹的子树中某个组件在渲染时抛出异常
- **THEN** `ErrorBoundary` 捕获该异常并渲染调用方传入的兜底内容，而不是让异常继续向上传播导致外层继续崩溃，同时生成一条包含组件堆栈的错误报告

#### Scenario: 支持自定义兜底内容
- **WHEN** 使用 `ErrorBoundary` 时传入了自定义的兜底展示内容
- **THEN** 捕获到错误后展示的是调用方传入的自定义内容，而不是固定不可变的默认文案

### Requirement: React 根节点级别的错误信号补充
系统 SHALL 通过 React 根节点提供的错误回调接收全局渲染错误信号，用于区分"错误被某个 `ErrorBoundary` 捕获并已恢复展示"与"错误完全没有被任何 `ErrorBoundary` 捕获"两种情况，并分别标记为不同的严重级别。

#### Scenario: 错误被某个 ErrorBoundary 捕获
- **WHEN** 渲染错误发生在某个 `ErrorBoundary` 的子树内并被该 `ErrorBoundary` 捕获恢复
- **THEN** 根节点同样收到该错误的信号，生成的错误报告严重级别为"错误"而不是"致命"

#### Scenario: 错误未被任何 ErrorBoundary 捕获
- **WHEN** 渲染错误发生在没有被任何 `ErrorBoundary` 包裹的子树中
- **THEN** 根节点收到该错误的未捕获信号，生成的错误报告严重级别为"致命"

### Requirement: 手动上报 API
系统 SHALL 导出一个手动上报函数，允许业务代码主动上报已经被 `catch` 处理、但仍需要留痕的错误，可附带调用方自定义的上下文信息，生成一条来源标记为"手动上报"的错误报告。

#### Scenario: 业务代码主动上报已处理的错误
- **WHEN** 业务代码在 `catch` 块中调用手动上报函数，传入错误对象和附加上下文
- **THEN** 系统生成一条来源标记为"手动上报"、包含该附加上下文的错误报告

### Requirement: 错误去重与节流
系统 SHALL 依据错误的消息与堆栈信息生成去重标识，对同一个去重标识在可配置的时间窗口内重复出现的错误进行合并：时间窗口内第一次出现时立即上报，窗口结束时补充上报一条包含累计出现次数的汇总记录，不允许窗口内每一次重复触发都单独调用上报出口。系统 SHALL 支持配置单个去重标识在窗口内的最大计数上限，达到上限时不必等待窗口到期即可提前结束窗口并发出汇总记录。

#### Scenario: 同一个错误短时间内重复触发
- **WHEN** 同一个去重标识对应的错误在去重时间窗口内被触发了多次
- **THEN** 系统只在窗口开始时上报一次，窗口结束时再补充上报一条附带累计次数的记录，中间的重复触发不会逐次调用上报出口

#### Scenario: 关闭去重
- **WHEN** 初始化时将去重时间窗口配置为关闭
- **THEN** 每一次错误触发都独立生成一条错误报告并调用上报出口，不做任何合并

#### Scenario: 达到单标识计数上限提前结束窗口
- **WHEN** 同一个去重标识在窗口未结束前的累计出现次数达到配置的计数上限
- **THEN** 系统立即结束该窗口、上报一条包含累计次数的汇总记录，不等待窗口自然到期；后续该标识再次出现时按照全新窗口重新计数

### Requirement: 部分错误可豁免去重
系统 SHALL 支持通过一个判定钩子决定某条错误报告是否参与去重，钩子判定不参与去重时该报告必须立即上报、不进入去重标识的计数体系；系统 SHALL 支持在手动上报 API 的单次调用上显式声明本次上报不参与去重，且调用点声明的优先级高于判定钩子。以上两种豁免均不影响全局节流。

#### Scenario: 判定钩子豁免某条错误
- **WHEN** 初始化时配置的判定钩子对某条错误报告返回不参与去重
- **THEN** 系统立即上报这条报告，不与其他相同去重标识的报告合并计数

#### Scenario: 手动上报单次调用声明不参与去重
- **WHEN** 业务代码调用手动上报函数时显式声明本次调用不参与去重
- **THEN** 系统立即上报这条报告，即使存在相同去重标识的其他报告仍在计数窗口内

### Requirement: 全局节流
系统 SHALL 支持配置一个与去重标识无关的全局节流阀，限制单位时间窗口内实际分发给上报出口的报告总数；超过上限后的报告默认被丢弃，但配置为豁免时致命级别的报告仍然放行且不计入丢弃统计。系统 SHALL 在节流窗口结束时，若该窗口内存在被丢弃的报告，补充上报一条包含丢弃数量的诊断记录；不配置全局节流时该能力不生效，行为与不存在这道限制完全一致。

#### Scenario: 短时间内出现大量不同错误被节流
- **WHEN** 全局节流窗口内不同去重标识的错误报告总数超过配置的上限
- **THEN** 超出上限部分的报告被丢弃，不分发给任何上报出口，窗口结束时补充上报一条包含本窗口丢弃数量的诊断记录

#### Scenario: 致命级别报告豁免节流
- **WHEN** 全局节流已达到上限且新到达的报告严重级别为致命
- **THEN** 该报告仍然被放行分发给上报出口，不计入本窗口的丢弃统计

#### Scenario: 未配置全局节流
- **WHEN** 初始化时未配置全局节流
- **THEN** 所有通过去重判断的报告都直接分发给上报出口，不受任何总量限制

### Requirement: 运行期间动态调整去重与节流策略
系统 SHALL 提供一个独立于初始化流程的配置接口，允许在应用运行期间中途调整去重与全局节流的策略，且不需要重新执行完整的初始化流程（不重复挂载全局监听器）。

#### Scenario: 运行期间调整去重窗口
- **WHEN** 应用运行期间调用该配置接口调整去重时间窗口
- **THEN** 之后新触发的错误按照新的去重窗口计算，不需要重新调用初始化函数、不重复挂载全局监听器

#### Scenario: 运行期间关闭全局节流
- **WHEN** 应用运行期间调用该配置接口将全局节流显式设置为关闭
- **THEN** 之后新触发的错误不再受总量限制，行为等同于从未配置过全局节流

### Requirement: 可插拔的上报出口
系统 SHALL 提供一个上报出口接口，允许在初始化时注册多个实现，每条错误报告都会被分发给全部已注册的实现；内置一个基于浏览器控制台输出的默认实现。

#### Scenario: 注册多个上报出口
- **WHEN** 初始化时注册了多个上报出口实现
- **THEN** 每一条错误报告都会依次分发给全部已注册的实现，其中任意一个实现内部抛出异常不影响其他实现正常接收到该报告

#### Scenario: 内置控制台上报出口的默认行为
- **WHEN** 只注册了内置的控制台上报出口
- **THEN** 每条错误报告都以结构化对象形式输出到浏览器控制台，而不是拼接后的字符串

### Requirement: 上报前的自定义过滤钩子
系统 SHALL 支持在初始化时传入一个过滤钩子，在错误报告分发给任何上报出口之前对其进行检查；该钩子判定应丢弃时，系统不得将该报告分发给任何已注册的上报出口。

#### Scenario: 过滤钩子丢弃指定错误
- **WHEN** 过滤钩子对某条错误报告判定为应丢弃
- **THEN** 系统不会将该报告分发给任何已注册的上报出口

#### Scenario: 未配置过滤钩子
- **WHEN** 初始化时没有传入过滤钩子
- **THEN** 系统直接将所有错误报告分发给已注册的上报出口，不做任何额外过滤
