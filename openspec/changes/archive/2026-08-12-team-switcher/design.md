## Context

`team-workspace-model` 让每个用户都归属若干 Team（含自动创建的个人 Team），但 Sidebar 目前只是把这些 Team 平铺列出，`WikiList`/`useWikiStore.wikis` 也是把用户能访问的全部 Wiki（不分 Team）混在一个数组里。`Wiki` 记录上已经带有 `teamId` 字段（后端接口未变），只是前端从未用它做过任何筛选或分组。这导致两个问题：浏览态分不清 Wiki 归属，编辑态更是完全没有"当前在哪个团队下"的提示。

参考 Notion/Slack 的 workspace 切换器：选中哪个 workspace，下面能看到的内容就唯一属于那个 workspace，但切换本身是纯前端状态切换（不整页刷新、不重新请求身份）。这份设计把这个模式落地到当前架构上。

## Goals / Non-Goals

**Goals:**
- 引入明确的"当前团队"（`currentTeamId`）概念，作为 Sidebar 团队区块内容（Wiki 列表、以后的文章树）的筛选依据
- 切换团队是瞬时的本地状态变化，不发路由跳转、不重新拉取 `wikis`/`teams`（数据已经在内存里，只是重新 filter）
- 打开一个不属于当前团队的 Wiki 时静默跟随切换，不打断用户操作
- 明确哪些 UI 元素划入"全局区"（不受当前团队筛选）：搜索、Home、置顶列表

**Non-Goals:**
- 不改变任何后端接口和权限判断逻辑（`GET /wikis` 语义不变）
- 不做"跨团队汇总"视图——这次明确收窄为"要么当前团队、要么全局搜索"两条路径，不做第三个中间态视图
- 不做"团队内独立的搜索范围切换"（比如"仅搜当前团队"选项）；搜索维持现有的全局范围不变
- 不涉及数据库结构变更

## Decisions

### 1. `currentTeamId` 是纯前端状态，不落库、不建新接口
Wiki 已经带 `teamId`，`teams`/`wikis` 数据本来就整份拉到前端内存里，筛选是一次 `Array.filter`，没有必要为"当前选中哪个团队"这件事引入服务端概念（那意味着要跨设备同步、要建表）。持久化到 `localStorage`（跟 `sidebarWidth` 一致的模式），不同设备/浏览器各自记住自己的选择，足够满足"刷新后保留上次选择"的需求。

**备选方案**：存到用户 profile（服务端）。放弃——这是一个纯 UI 偏好，不是业务数据，没必要引入同步复杂度。

### 2. 默认值与初始化：优先个人 Team，其次 localStorage 记住的值
首次登录（`localStorage` 里没有记录）默认选中用户的个人 Team（`teams.find(t => t.isPersonal)`）；此后每次切换都覆盖写入 `localStorage`，下次打开直接读取；如果 `localStorage` 里的 `teamId` 已经不在当前 `teams` 列表里（比如被移出了那个团队），回退到个人 Team。

### 3. 团队区块的筛选边界：Wiki 列表和以后的文章树在内，置顶、搜索、Home 在外
`Sidebar` 结构划分为"全局区"（搜索入口、Home 链接、置顶列表）和"团队区"（团队切换器 + 当前团队的 Wiki 列表 + 新建入口）。置顶特意划进全局区而不是团队区——因为置顶的存在价值就是"不管我在哪都能一键跳过去"，如果被当前团队筛掉，等于跟着团队切换而"消失"，用户会以为丢了数据。

### 4. `/wiki` 列表页收紧为当前团队视图，不保留跨团队汇总（**BREAKING**）
`WikiList.tsx` 改为读取 `currentTeamId` 后 `useWikiStore.wikis.filter(w => w.teamId === currentTeamId)`。"我忘了某个 Wiki 在哪个团队"这类需求交给现有的全局 `SearchDialog`（本来就是跨团队检索），不重复建设第二个跨团队浏览入口——两个跨团队路径（列表 + 搜索）会互相冗余且行为不一致，只留搜索一条路径边界更干净。

### 5. `CreateWikiDialog` 移除团队选择器，直接使用 `currentTeamId`
`team-workspace-model` 里给创建对话框加的"属于多个 Team 时展示选择列表"这条交互被切换器取代——用户在点"新建 Wiki"之前已经通过 Sidebar 顶部的切换器表明了"我现在在哪个团队下工作"，创建时不需要再选一次。

### 6. 跨团队打开 Wiki 时静默切换 `currentTeamId`，不弹确认
`WikiDetail`（或以后的专属 Shell）挂载时读取 `wiki.teamId`，与 `currentTeamId` 不一致就直接 `setCurrentTeamId(wiki.teamId)`——这是保持"感知不到硬切换"体验的关键：用户唯一能感觉到的是 Sidebar 顶部团队名变了，不会有弹窗打断阅读/编辑操作。

## Risks / Trade-offs

- **[风险] `localStorage` 记住的 `teamId` 在多设备间不一致** → 可接受，这是纯 UI 偏好而非业务状态，不影响数据可见性（`GET /wikis` 权限判断完全不受影响，只是本地展示筛选）
- **[风险] 静默切换可能让用户"不知道自己已经换了团队"，误在错误团队下新建 Wiki** → Sidebar 顶部切换器本身要保持醒目（当前团队名一直可见），且这次不做"跨团队汇总创建"路径——新建入口只出现在团队区块内，创建的 Wiki 归属永远等于当前可见的那个团队名，不存在"看不到就误操作"的空间
- **[权衡] 放弃跨团队 Wiki 汇总视图，对"团队很多、记不清在哪个团队"的用户不友好** → 用搜索兜底；如果后续验证发现搜索不够用，再考虑加回一个轻量的"最近访问"跨团队列表，但不在这次范围内

## Migration Plan

- 无数据库迁移；纯前端改动，一次性上线即可，不需要分阶段
- 上线后首次打开：`localStorage` 无记录 → 自动回退到个人 Team，行为等价于"什么都没变"，不会有迁移中断感
- 回滚：直接回退前端构建版本即可，不涉及任何后端/数据状态需要还原
