## Context

`apps/api/src/services/storage.ts` 目前的 `uploadImage` 是无状态的：每次调用都对输入 buffer 做 `sharp` 转码（转 WebP + 限宽 1600px），再无条件写入 MinIO 生成一个新的 objectKey。没有任何机制记录"这份内容之前是否已经上传过"，也没有任何机制在封面图被替换/清空、或 Wiki/Document 被删除时清理曾经写入的对象——objectKey 一旦生成，只要没人手动去 MinIO 控制台删，就永久占用存储。这是目前唯一的图片上传入口（Wiki 封面、Document 封面共用同一套逻辑）。

## Goals / Non-Goals

**Goals:**
- 相同原始内容的重复上传不再各自占用独立的存储对象与转码算力
- 在现有会"替换/清空封面图"和"删除 Wiki/Document"的写路径上，正确维护引用计数
- 引用计数归零时尽力（best-effort）物理删除对象，减少长期存储占用
- 不改变现有上传接口的请求/响应契约，前端零改动

**Non-Goals:**
- 不做"视觉相似但字节不同"的图片去重（比如同一张图被两个不同工具重新编码后字节不同）——只做原始文件内容的精确哈希匹配
- 不回填本能力上线前已经产生的历史对象——历史 URL 不会出现在新的追踪表里，第一次被替换/清空时按"未追踪"处理（无操作），见下方 Decisions
- 不做定时扫描孤儿对象的清理任务（比如物理删除失败后留下的、或本能力上线前产生的孤儿对象）——只做同步的 best-effort 删除
- 不引入内容审核/敏感内容检测

## Decisions

**1. 哈希对象选择：原始上传 buffer，而不是转码后的 WebP buffer**
对用户上传的原始文件内容计算哈希（而不是等 `sharp` 转码完再哈希）。这样命中去重时可以完全跳过转码这一步 CPU 开销；代价是"同一张图片、不同原始编码"不会被识别为重复——这属于可接受的 Non-Goal，去重目标是"完全相同的重复上传"这个最常见场景（用户重复选中同一个文件、或多个 Wiki 恰好用了同一份素材文件）。

**2. 追踪表设计：一张表、两个唯一索引**
新增一个记录（暂命名 `UploadedObject`）：`sha256`（唯一，供上传时去重查找）、`url`（唯一，供替换/清空封面图时按值反查）、`bucket`、`objectKey`、`size`、`mimeType`、`refCount`（默认 1）。
- 之所以需要 `url` 这个独立的唯一索引：释放引用时（封面图被替换/清空）调用方手上只有"旧的 URL 字符串"，没有原始文件内容，无法重新计算 `sha256` 去反查——必须能直接按 URL 命中。
- 这张表设计上不绑定"covers"这个具体 bucket（字段里有 `bucket`），是为了未来如果有其他上传场景想复用同一套去重机制时不需要重新建表；但本轮只有图片这一个消费方，不做进一步抽象。

**3. 并发上传相同新内容的处理：唯一约束 + 插入失败转自增，而不是显式加锁**
两个请求几乎同时上传同一份"从未出现过"的内容，都会先转码再尝试插入一条 `refCount=1` 的新记录——利用 `sha256` 唯一索引，后到的那次插入会因唯一约束冲突失败，此时按"命中"逻辑重新查询该记录并执行 `refCount + 1`（原子自增）。
- 备选方案：用 Postgres advisory lock 或者应用层分布式锁在查找前加锁——排除，图片上传本身不是高频热点路径，为一个低概率的竟态引入额外的锁基础设施不划算，"插入失败即重试为自增"足够简单且正确。
- 代价：后到的那次请求仍然会执行一次多余的转码与一次多余的（随后被丢弃的）MinIO 写入——接受这个代价，因为它只发生在"两个请求几乎同时上传同一份全新内容"这个窄窗口内，不是常态。

**4. 释放引用的触发点：写路径显式调用，不做全局钩子/中间件**
在 `updateWikiInfo`/`updateDocument` 里，写入新的 `coverImage` 之前先读出旧值，写入成功后如果旧值非空且与新值不同，调用 `releaseImageRef(oldUrl)`；`deleteWiki`/`deleteDocument` 删除记录前，如果该记录 `coverImage` 非空，同样调用 `releaseImageRef`。
- 备选方案：在 Prisma 层用 middleware/extension 统一拦截所有对 `coverImage` 字段的写入——排除，Prisma 中间件的字段级"before/after"差异感知不直观，容易漏掉某个路径或误伤批量操作，显式调用更容易审查正确性。

**5. 引用计数归零后的物理删除：同步 best-effort，不进队列**
`refCount` 自减后如果归零，立即在同一次请求处理中调用 MinIO 删除，包一层 try/catch——失败只记录日志，不回滚刚才对 `coverImage`/记录本身做的任何变更（元数据变更是"这份内容不再被引用"这一事实的真相来源，物理对象是否真的删干净属于次要的存储优化）。
- 备选方案：物理删除放进一个异步队列（类似 `video-hls-embed` 变更里给转码用的那种）——排除，本仓库当前没有队列基础设施，为了一个"最多是打个日志失败"的操作引入队列不划算；如果后续视频变更真的引入了 BullMQ，可以考虑让这里也复用，但不在本轮预先假设。

## Risks / Trade-offs

- [Risk] 去重命中直接复用旧记录的 URL，但如果该对象在 MinIO 里已经被人手动删除（或此前物理删除失败留下的"数据库有记录、对象已丢失"的不一致），命中后返回的 URL 会指向一个不存在的对象，前端展示会 404 → [Mitigation] 本轮不在每次命中时都额外发一次 `HEAD` 请求校验对象是否存在（会抵消去重节省的开销），这个不一致场景发生概率低，记录为 Open Question，后续可以考虑加一个低频的定期校验/自愈任务
- [Risk] 并发上传相同新内容时，后到请求的转码与一次多余的 MinIO 写入是浪费的算力/带宽 → [Mitigation] 见 Decisions 3，接受这个代价，不引入额外锁机制
- [Risk] 物理删除失败会累积孤儿对象（DB 认为已经没有引用了，但 MinIO 里对象还在） → [Mitigation] 只是浪费存储，不影响正确性；不在本轮做定期清理任务，留作后续独立工作

## Migration Plan

1. 新增 Prisma migration 建 `UploadedObject` 表，不回填任何历史数据——历史封面图 URL 从此就是"未追踪"状态：它们永远不会在 `sha256` 去重查找中被命中（因为表里没有它们的记录），也永远不会在被替换/清空时触发引用计数变更（`releaseImageRef` 按 `url` 查不到记录时是无操作），行为上完全等同于"这个功能上线前就没有这套机制"，安全、无副作用。
2. 部署顺序：先跑迁移建表，再发布新代码；旧代码在迁移之后、发布之前这段时间正常运行，不读写新表，不受影响。
3. 回滚：如果只回滚代码保留表，旧代码不访问这张表，无影响；如果要连表一起回滚，由于表没有被任何其他功能依赖，直接 drop 即可。

## Open Questions

- 是否需要一个低频的定期校验/自愈任务，检测"记录存在但物理对象已丢失"或"物理对象存在但记录已经归零未清理"这两类不一致——本轮不做，留待后续视情况评估
- 如果未来视频变更（`video-hls-embed`）也需要类似的引用计数机制，是否要把这张表泛化成一个跨业务类型的通用"对象引用登记表"——本轮不预先做这个抽象，保持当前设计只服务图片场景
