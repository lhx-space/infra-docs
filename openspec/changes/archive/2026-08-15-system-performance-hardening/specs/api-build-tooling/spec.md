## ADDED Requirements

### Requirement: 生产构建产物的正确生成
`apps/api` 的生产构建 SHALL 生成可直接运行的 `dist` 产物，构建过程 MUST NOT 要求源码中的相对导入路径显式携带文件扩展名；构建产物中对原生依赖、数据库/缓存客户端、外部二进制调用、Prisma 生成客户端等运行时依赖的引用 MUST 保持可被 Node.js 正常解析加载，不因构建过程被改写或内联。

#### Scenario: 构建成功产出可运行产物
- **WHEN** 对 `apps/api` 执行生产构建命令
- **THEN** 构建成功完成，产出的 `dist` 目录下的入口文件可以被 `node` 直接启动

#### Scenario: 源码相对导入无需文件扩展名
- **WHEN** 源码中存在不带文件扩展名的相对路径导入
- **THEN** 构建过程正常处理该导入，不产生因缺少扩展名而导致的构建错误

#### Scenario: 运行时依赖在构建产物中保持可加载
- **WHEN** 构建产物启动后执行到依赖原生二进制、数据库/缓存客户端或 Prisma 生成客户端的代码路径
- **THEN** 对应依赖被正常加载，不出现"模块未找到"或路径解析错误

### Requirement: 类型检查与构建产物生成相互独立
`apps/api` 的类型检查步骤 SHALL 与生产构建产物的生成步骤使用各自独立的工具/配置，类型检查的模块解析设置的变更 MUST NOT 影响构建产物的生成方式，反之亦然。

#### Scenario: 类型检查失败不阻塞已生成的构建产物定义
- **WHEN** 类型检查步骤发现类型错误
- **THEN** 该错误通过独立的类型检查步骤报告，不改变构建产物生成步骤本身的行为约定

### Requirement: api 服务的多核利用
生产环境下的 `api` 服务 SHALL 以多进程方式运行以利用多核资源；`worker`（异步任务消费者）服务的运行方式与并发配置 MUST NOT 因此发生变化。

#### Scenario: api 服务多进程运行
- **WHEN** `api` 服务在生产环境启动
- **THEN** 系统以多个工作进程处理请求，共享同一个监听端口

#### Scenario: worker 服务并发行为不受影响
- **WHEN** `api` 服务引入多进程运行方式后，`worker` 服务照常启动
- **THEN** `worker` 服务仍以既有的单进程方式运行，其任务并发上限配置值不因 `api` 的多进程化而改变实际生效的并发数
