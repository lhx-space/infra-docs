## ADDED Requirements

### Requirement: 捕获 WebSocket/SSE 连接级失败
系统 SHALL 提供一个显式的注册函数，允许消费方把一个 `WebSocket` 或 `EventSource` 实例接入监控；接入后，系统 SHALL 在该连接建连失败、以非正常状态关闭、或反复重连仍不成功时，生成一条来源标记为"网络连接失败"的错误报告，包含连接的分类标识（`websocket`/`sse`）与消费方可选提供的标签；系统 SHALL NOT 采集连接建立成功后的单条消息级错误，也 SHALL NOT 采集常规 HTTP 请求的失败或状态码信息。

#### Scenario: WebSocket 建连失败
- **WHEN** 已注册的 `WebSocket` 实例触发 `error` 事件或以非正常状态码关闭
- **THEN** 系统生成一条来源标记为"网络连接失败"的错误报告，标注连接分类为 `websocket`

#### Scenario: SSE 连接失败
- **WHEN** 已注册的 `EventSource` 实例触发 `error` 事件
- **THEN** 系统生成一条来源标记为"网络连接失败"的错误报告，标注连接分类为 `sse`

#### Scenario: 未注册的连接不产生报告
- **WHEN** 一个 `WebSocket`/`EventSource` 实例从未被显式注册接入监控
- **THEN** 该实例的任何连接失败都不会生成错误报告

#### Scenario: 正常关闭不产生报告
- **WHEN** 已注册的 `WebSocket` 实例被消费方主动、以正常状态码关闭
- **THEN** 系统不生成任何错误报告

### Requirement: 网络错误的链路追踪 id 提取与关联
系统 SHALL 在错误报告协议中提供一个可选的链路追踪标识字段；系统 SHALL 支持在初始化时配置一个提取钩子，该钩子接收一次"未处理的 Promise 拒绝"或"手动上报"场景下的原始错误值，判断其是否为网络请求错误并尝试提取链路追踪标识；提取成功时，系统 SHALL 将提取到的标识写入对应错误报告的链路追踪字段。未配置该钩子或钩子判定不是网络请求错误时，系统 SHALL 不填充该字段。

#### Scenario: 未处理的网络请求错误被提取到追踪标识
- **WHEN** 一个未被业务代码捕获的网络请求错误变成未处理的 Promise 拒绝，且已配置的提取钩子能从中识别出链路追踪标识
- **THEN** 生成的错误报告携带该链路追踪标识

#### Scenario: 手动上报网络请求错误
- **WHEN** 业务代码 `catch` 住一个网络请求错误后调用手动上报函数，且已配置的提取钩子能从中识别出链路追踪标识
- **THEN** 生成的错误报告携带该链路追踪标识

#### Scenario: 非网络错误不填充追踪标识
- **WHEN** 未处理的 Promise 拒绝或手动上报的错误值被提取钩子判定为不是网络请求错误
- **THEN** 生成的错误报告不携带链路追踪标识字段

#### Scenario: 未配置提取钩子
- **WHEN** 初始化时未配置链路追踪提取钩子
- **THEN** 所有错误报告都不携带链路追踪标识字段，其余采集行为不受影响

### Requirement: 服务端响应携带可关联的链路追踪标识
`apps/api` SHALL 在每一个 HTTP 响应中携带一个响应头，值为该请求在服务端生成的、已写入服务端结构化日志的唯一标识；该标识 SHALL 在成功响应与错误响应中均存在，不因请求处理结果而缺失。

#### Scenario: 成功响应携带追踪标识
- **WHEN** 客户端发起一次请求并收到 `2xx` 响应
- **THEN** 响应头中包含该请求的追踪标识，且该标识与服务端针对该请求打的日志行使用同一个值

#### Scenario: 错误响应同样携带追踪标识
- **WHEN** 客户端发起一次请求并收到非 `2xx` 响应
- **THEN** 响应头中依然包含该请求的追踪标识

### Requirement: 基于本地持久化队列的 HTTP 上报出口
系统 SHALL 提供一个内置的、endpoint 可由消费方配置的 HTTP 上报出口实现。每一条错误报告产生后，该实现 SHALL 先同步写入本地持久化存储（不等待任何网络往返），再尝试通过网络发送；网络发送成功后 SHALL 将该条从持久化存储中移除，发送失败或未能在当前页面生命周期内确认送达时 SHALL 保留在持久化存储中。应用下一次启动时，该实现 SHALL 读取持久化存储中尚未确认送达的报告并重新尝试发送。该实现 SHALL 支持携带自定义请求头。发送失败时，系统 SHALL 仅记录到控制台，SHALL NOT 因此再次触发一轮错误上报。

#### Scenario: 正常发送错误报告
- **WHEN** 已注册该 HTTP 上报出口且产生了一条需要分发的错误报告
- **THEN** 系统先将该报告写入本地持久化存储，随即向配置的 endpoint 发出一次携带该报告内容的请求；请求成功后该报告从持久化存储中移除

#### Scenario: 发送失败后保留在本地队列
- **WHEN** 该 HTTP 上报出口尝试发送一条报告但网络请求失败
- **THEN** 该报告继续保留在本地持久化存储中，不被丢弃

#### Scenario: 应用下次启动时补发未确认送达的报告
- **WHEN** 应用启动，本地持久化存储中存在此前未确认送达的错误报告
- **THEN** 系统对这些报告重新发起发送尝试

#### Scenario: 页面卸载时的机会性发送不影响持久化保障
- **WHEN** 页面即将隐藏或卸载，本地持久化存储中存在尚未确认送达的报告
- **THEN** 系统尝试一次机会性发送；无论该次尝试是否成功，报告在成功送达前均保留在本地持久化存储中，不因该次尝试的结果而丢失

#### Scenario: 上报请求本身失败不引发自我循环
- **WHEN** 该 HTTP 上报出口发出的请求本身失败
- **THEN** 系统仅将该失败记录到控制台，不会因此生成新的错误报告

## MODIFIED Requirements

### Requirement: 统一的错误上报协议
系统 SHALL 将所有来源（渲染错误、全局同步异常、未捕获 Promise rejection、静态资源加载失败、网络连接失败、手动上报）产生的错误统一收敛为同一个 `ErrorReport` 数据结构，包含来源标识、严重级别、错误消息、堆栈、发生时间、当前页面地址、User Agent、可选的链路追踪标识等字段；不同来源仅通过来源标识字段区分，不允许各来源自行定义不同的报告结构。

#### Scenario: 不同来源产出同一套字段结构
- **WHEN** 一次全局同步异常和一次 React 渲染错误分别被捕获
- **THEN** 两者生成的错误报告具有完全相同的字段集合，仅来源标识与是否携带组件堆栈不同

#### Scenario: 网络连接失败与其他来源共用同一套字段结构
- **WHEN** 一次 WebSocket 连接失败被捕获
- **THEN** 生成的错误报告与其他来源的报告具有完全相同的字段集合，仅来源标识、以及是否携带链路追踪标识不同
